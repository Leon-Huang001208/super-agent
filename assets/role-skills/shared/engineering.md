# 工程规范

仅在编码、调试或实质配置变更时读取。Paperclip 的岗位职责由对应角色说明提供，项目命令和约束以项目规则为准；这里保留用户共同的工程要求。

## 工程原则与执行

- 所有本机开发的 Git 仓库和工作树都放在不受云盘同步管理的本地目录（如 `~/Developer`）。跨设备通过 Git 远端同步源码。
- 从上下文和现有实现确认目标、约束与验收，自主推进已授权工作直至交付。已有授权持续有效，仅在关键信息缺失、确需新增授权或具体阻塞无法自行解决时提问，并说明依据。
- 区分事实、假设和未验证事项。用低成本、可逆的检查消除关键不确定性，按实际风险选择最小可行修复并继续执行。
- 复用已有入口、实现和有效证据，核对接口契约、失败传播及恢复方式。自行引入的限制或错误解释应在源头纠正。
- 避免过度防御性编程。聚焦当前需求与受支持输入，不因假设性风险增加审批、验收门、流程、锁、回执、抽象层、重复守卫或无用兼容分支。
- 修改文件前先读取。保持改动聚焦、可审查，按风险和并发情况选择必要的隔离。
- 修改已有文件优先使用 Edit 或 apply_patch 等局部编辑；保留不相关改动。
- 所有代码必须有明确错误处理并记录日志，日志使用项目的 `logs/` 目录；复用项目既有日志接口，日志不记录秘密。
- 对实际失败明确处理并记录可定位的日志，避免静默降级。遇到问题持续诊断和修复，避免用反复检查或只交方案替代执行。

## 验证与交付

- 验证与改动风险相称，优先运行已有的相关检查。新增测试聚焦具体回归风险。
- 已通过的检查，仅在新改动、新失败或未解决疑点需要时重复或扩大。
- 按当前任务授权和项目要求完成交付。发布、部署、迁移及破坏性操作遵循相应授权与验收。
- 交付说明应准确记录完成内容、验证结果和待办，分别说明发布、部署与业务验收状态。
- 收尾清理本任务可确认归属且已无用途的临时资源，保护未归并工作、业务数据、凭据和恢复证据。

## 工具与协作

- 独立只读检查批量执行。等待任务或 CI 时，状态无变化则静默。
- 网页操作优先使用可用的 CLI/API，其余使用已登录的 Chrome。飞书优先使用 lark-cli。
- 仅在任务真正独立且能节省时间或提高质量时委派子 Agent，明确输入、输出和完成判据，由主 Agent 汇总验证。
- 安装 Python 包前说明用途并取得同意。Python 优先使用项目环境，无项目约定时使用 /opt/homebrew/bin/python3.12。
- 修改 Skill 时同步更新该 Skill 的文档。
