# 按当前任务推进

本资料按模式使用。不要因为有八个模式，就要求用户依次完成八轮。

<a id="coaching"></a>
## 教练节奏

对新手，采用“白话解释 → 当前产品的小例子 → 一次能完成的练习 → 判断标准”。先让用户完成一项真实决定，再介绍下一项能力。首次出现术语用一句话解释，例如“PRD，即产品需求说明，让实现者知道要做什么和怎样验收”。

推荐学习顺序：产品与客户 → 客户任务和证据 → 竞品借鉴 → 需求取舍 → 产品规格 → 数据和AI → 协作验收 → 试用复盘。它是自定进度的路径，不是时间承诺。任务需要跳到某章时直接进入。

练习优先产出可复用材料：一段产品说明、一条客户任务、一个带证据的需求、一份小功能规格、几条验收用例。反馈说清“哪里已足够、哪里缺证据、怎样补”，避免用“没有产品sense”等抽象评价。

<a id="discovery"></a>
## 发现问题

把“要一个功能”还原为“谁在什么情况下要完成什么任务，现有做法在哪里受阻”。角色、决策人、购买方可能不同；只有与当前需求有关时才区分，不先画完整组织图。

访谈围绕最近一次具体经历：触发了什么任务、用过哪些资料或工具、花在哪一步、怎样判断结果、失败的代价、曾经如何解决。先听实际经历，再讨论拟议方案。记录原始描述与自己的解读，不能把一句偏好升级为已验证需求。

用已有授权反馈、行为记录和访谈互相核对。没有客户访问条件时，提出可由用户执行的访谈或小规模试用，不模拟真实访谈结果。产出问题假设及证据缺口；只有用户需要时才生成完整提纲。

**例：**“客户要加AI问答”可暂写为“某类客户在查找研究结论及出处时可能耗时；AI问答是候选办法”。下一步确认最近一次查找任务和现用方法，而不是直接定义一个通用聊天机器人。

<a id="competitive"></a>
## 竞品借鉴

先问本次要借鉴什么：客户任务、信息组织、交互、数据或业务能力。已有壳子时复用观察资料，按需核对现状，不自动全站逆向。

每个重点功能记录：观察到什么、可能支持什么任务、何种条件下有用、对当前客户是否成立、尚不清楚的数据/算法/权限条件。把“看得见的界面行为”和“推断的运行机制”分开。

产出可借鉴、需修改、暂不采用三类建议并说明理由。没有需求证据时可制作教学假设或待验证清单，不声称竞品已经证明效果。

<a id="priority"></a>
## 需求取舍

比较当前目标下的候选项：客户任务价值、出现的证据、处理紧迫性、成本与依赖、关键不确定性、可逆性。成本未知先给范围或要求实现方估算，不编造人日。

给出先验证、先交付、暂缓的建议及理由。高价值但证据弱的项可先安排低成本验证；必要前置项应说明它支撑的客户结果。相互独立的需求不必被塞进同一版本。

定义最小验证范围时，至少保留能完成一个任务的完整路径，包括需要的空态、失败态与结果解释。不要只按页面数量或控件数量切分。

**例：**“一周做十个功能”先列目标、已知资源、必须完成的客户任务与依赖。给一个可讨论的小范围建议，并明确工期须由实现方确认。不要靠降低验收或编造价值分数承诺全部完成。

<a id="specification"></a>
## 规格设计

使用当前任务所需粒度：小修改可用背景、规则变化和验收三部分；新流程再增加角色、入口、主流程、异常、数据和范围。模板只作提醒，不作统一文档门槛。

需求应让接收者能观察结果。把“好用、准确、智能、专业”转成具体任务和判定办法；目标值须来自基线、业务要求或明确标记的试验假设。

核心验收写成“在某前提下，执行某操作，应得到某可观察结果”。覆盖有实际风险的空结果、无权限、加载失败、重复提交和数据过期等状态，不给每个小改机械堆全套边界。

数据或规则不明时，先列待确认项、代表样本和决定者。视觉还原、可点击、接口可用、结果正确、客户能完成任务是不同的检查，不把前者当作全部验收。

<a id="data-ai"></a>
## 数据与AI问题

先定位差异发生在哪一层：输入对象/日期、数据来源、字段含义、计算口径、筛选与排序、显示精度、展示状态，或AI的检索/推断/呈现。保留双方同条件样本，不先认定是代码错或参考站正确。

金融任务读取 [finance.md](finance.md)。一般软件任务只保留相关的来源、时效、定义、基准和失败处理。

AI功能须明确任务、可用证据、允许的操作和怎样评测。用典型正确案例、信息不足、相互冲突和无关提问检验；不能靠演示中一两次看似流畅的回答验收。

<a id="delivery"></a>
## 交付协作

交给AI：给出目标、已有事实与材料、限定范围、业务规则、验收例子及未决项。实现方式属于接收方职责；只有已有约束或具体误实现风险时才规定技术。需要拆任务时按能独立验证的行为拆，不承诺无证据的排期。

交给研发团队：使用同一份产品决定和验收依据，补齐相关角色责任、依赖、估算来源与版本范围。记录评审发现及变更原因，避免会话、原型、需求文档出现多个现役答案。

检查AI或研发交付时，区分“未实现、与规格不符、规格缺失、验收资料不足”。引用可复现的操作和结果；没有运行证据就写待验收，不宣称通过。实现后的新建议放回需求池，除非影响当前目标，不临时扩大范围。

<a id="retrospective"></a>
## 试用复盘

从客户任务定义成功，例如能否在预定条件下完成比较并找到结论出处。再观察完成率、所需时间、理解偏差、返回修改与重复使用；选择真正能获取的指标。

基线、观察窗口、样本来源和统计分母要说明；样本少时描述案例，不伪装总体比例。不以点击量或好评单独证明业务价值。

复盘分别记录观察事实、原因假设、下一项验证和决定。保留不采用某建议的理由；“继续观察”应对应明确要补的证据，避免无限等待。
